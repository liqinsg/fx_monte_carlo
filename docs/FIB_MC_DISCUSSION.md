## 1. 项目背景与总体目标

本系列讨论围绕两个现有项目展开：

-   `fx_monte_carlo`：负责 Monte Carlo（MC）统计分析及 Fibonacci
    相关结构/产物的生成。
-   `forex_oanda_v7`：负责消费研究产物，并在 OANDA Practice Demo
    环境中执行交易策略。

目标不是再增加一个孤立指标，也不是用单一模型预测市场方向，而是建立一个**能够持续观察当前市场、识别市场状态变化、评估不确定性，并对新
Entry 作出有依据的许可或暂停决策**的系统。

核心问题包括：

1.  Bot 启动时间不同，是否会造成观察窗口和交易结果差异？
2.  市场在启动后发生变化时，系统能否及时适应，而不是继续依赖启动时的旧判断？
3.  强趋势、阶梯式趋势、窄幅/宽幅震荡等不同环境，是否需要不同的 Entry
    许可条件？
4.  TP 后市场状态是否发生变化，导致后续交易更容易 SL？
5.  某些开仓时段是否更容易先触及 SL，即使价格之后朝原交易方向运行？
6.  Bot 重启或维护后，已有仓位是否会不合理地抑制新 Entry 评估？

原则上，统计方法应被认真使用；若统计方法有问题，应通过证据改进，而不是因为它不能给出确定答案就放弃。市场本身存在不确定性，系统应管理不确定性，而不是假装消除不确定性。

## 2. 已明确的设计原则

### 2.1 以真实 Demo 验证为目标

-   首轮集成只使用 OANDA **Practice Demo**，不得连接 Live 账户。
-   MC、Fib、Kalman 和市场环境观察不能只写日志；它们必须实际参与 Demo
    的当前新 Entry 许可判断。
-   不能只用过时的历史观察结果来决定今天的交易。今天/最近可获得的数据必须能够影响当前
    Entry。
-   不应无限停留在
    RFC、文档和局部测试循环中。先定义足够清楚、可测试、可审计的边界，然后进入隔离的
    Demo 实践验证。
-   第一阶段只控制**新 Entry**。不改变已有持仓的 SL/TP
    管理逻辑，不擅自改变现有策略规则。

### 2.2 先观察和验证，不急于改策略

-   不预先认定某个时段、节假日或指标必然导致亏损。
-   先建立交易生命周期和市场观察证据，再决定是否需要调整规则。
-   未知或无法识别的市场模式应明确标记为 `UNKNOWN_PATTERN`，并采取
    `NO TRADE`，而不是强行归类。
-   对每项结论保留样本量、时间范围、数据来源和不确定性。

### 2.3 启动时间不应成为市场时间原点

Bot
在任意时间启动，都应能够恢复有效状态并继续观察市场。启动时间不应决定市场周期的定义，也不应让系统把启动前的有效市场信息全部丢弃。

### 2.4 现有仓位与新 Entry 评估必须解耦

用户特别指出：维护或重启后，如果 Bot 已经有持仓，Bot
可能变得过度谨慎，甚至不再积极评估新的交易机会。

需要明确区分：

1.  **Market Observation**：持续观察市场，不应因为账户已有仓位而停止。
2.  **Existing Position
    Management**：继续按现有规则管理已有仓位；第一轮保持不变。
3.  **New Entry
    Evaluation**：独立评估新机会，不应把"已有仓位"直接等同于"禁止评估/禁止交易"。

是否允许同品种、同方向或反向加仓，应由明确的风险规则决定，不能由模糊的全局持仓锁代替。

## 3. 候选系统架构

整体职责建议保持分离：

``` text
fx_monte_carlo
    ├── Daily Anchor MC
    ├── Daily Anchor Fibonacci
    ├── Rolling MC
    └── Rolling Fibonacci
             │
             ▼
    可审计、带时间戳和数据语义的研究产物
             │
             ▼
forex_oanda_v7
    ├── Market Context
    ├── Kalman State Estimator
    ├── Regime Controller
    ├── Entry Decision
    └── OANDA Practice Demo
```

`fx_monte_carlo` 负责研究和生成统计产物；`forex_oanda_v7`
负责读取产物、结合实时观察，并决定是否允许新
Entry。两者之间应通过清晰、版本化、可验证的接口通信，而不是复制粘贴内部实现。

### 3.1 Daily Anchor MC / Fib

-   每日 UTC 00:00 建立 Daily Anchor（新加坡时间 08:00）。
-   使用符合定义的已完成行情数据，明确数据截止时间，避免 look-ahead。
-   Daily Anchor MC 生成当日统计基线；Daily Fib 从该 Anchor
    的定义和坐标体系中产生。
-   Daily Anchor 是当日比较基准，应保留用于审计，不被 Rolling 结果覆盖。
-   它不是全天不变的交易信号，也不应单独决定是否开仓。

### 3.2 Rolling MC / Fib

-   Rolling MC
    根据最近可用数据持续更新，初步讨论的候选更新频率为每小时。
-   每次更新必须记录数据截止时间、输入数据范围、生成时间、版本和质量状态。
-   Rolling Fib 应从对应的 Rolling MC/当前定义独立计算。
-   **Daily Fib 与 Rolling Fib
    属于不同坐标体系，不得混用或把其中一个误当成另一个。**
-   Rolling 结果用于表达当前市场相对 Daily Anchor 的变化，并参与新 Entry
    的许可判断。
-   过期、缺失或数据质量不合格的 Rolling 产物不能被当作当前有效判断。

### 3.3 Monte Carlo 语义必须准确

至少保留以下定义：

-   `p_up`：模拟终点价格高于当前价格的路径/模拟比例；它不是交易胜率，也不是某笔交易盈利概率。
-   `touch_upper_pct` /
    `touch_lower_pct`：模拟路径中曾触及上/下边界的比例；它们不是 TP
    达成概率。
-   路径触及概率、终点分布和实际交易结果是不同概念，报告和接口不得混淆。

## 4. Kalman Filter 的定位

讨论采用汽车定位的直观类比：系统不断根据上一状态预测位置，再利用新的观测修正估计，同时维护估计的不确定性。

候选 FX 原型采用简单的局部趋势状态：

``` text
State = [Level, Drift]
```

-   `Level`：估计的潜在价格水平。
-   `Drift`：估计的局部斜率/变化速度。
-   `Uncertainty`：状态估计的不确定性（例如协方差）。
-   `Innovation`：实际观测值与预测值之间的偏差。

基本循环：

``` text
Predict → Observe → Update → Repeat
```

关键参数语义：

-   `Q`：过程噪声，控制模型允许状态变化的程度。较高通常更灵敏，但也可能更噪。
-   `R`：观测噪声，控制对新观测的信任程度。较高意味着降低单次观测对估计的影响。
-   `Innovation_t = Actual_t - Predicted_t`。

限制和注意事项：

1.  Kalman 是状态估计器，不是 BUY/SELL 预测器。
2.  它不会自动识别所有市场结构，也不能凭空创造预测优势。
3.  它不是简单保存全部历史原始数据；它递归更新状态和协方差。原始观测仍应保留，以便审计和回放。
4.  Kalman 不确定性带与 MC 未来价格分布不是同一个概念。
5.  持续 Innovation
    偏大可能表示模型与当前市场不匹配，但不能单凭一次偏差就宣布市场
    regime break。
6.  合成数据中可用 MSE
    检查估计质量；真实市场没有直接可观测的"潜在真实状态"，MSE
    较低也不等于有交易优势。
7.  需要用
    Demo/历史回放验证它能否帮助区分正常回撤、趋势减弱和可能的状态变化，同时避免过度反应。

## 5. Market Context 与 Regime Controller

### 5.1 两类 Context 必须分开

**Calendar Context（已知日历背景）**

例如：

-   新加坡公共假期及长周末；
-   中国农历新年；
-   Christmas / New Year；
-   其他可能影响特定市场参与者或交易时段的节假日。

日历事件应记录阶段，例如：

-   `BEFORE_HOLIDAY`
-   `DURING_HOLIDAY`
-   `AFTER_HOLIDAY`

**Observed Context（实际观察到的市场状态）**

例如：

-   Spread；
-   市场活动程度、报价/成交更新频率；
-   波动率；
-   数据新鲜度、缺口；
-   Kalman Level、Drift、Innovation；
-   Rolling MC 相对 Daily Anchor 的偏离；
-   Fib 所在区域。

节假日是一个先验背景提示，不是自动停交易开关。需要用实际市场活动和具体货币对的表现来验证影响。

### 5.2 春节等节日不能简单使用布尔开关

中国农历新年日期每年变化，市场影响可能在节前逐渐形成、节日期间持续、节后逐渐恢复。它与固定日期的
Christmas 等事件不同。

新加坡长周末可能影响亚洲时段的参与度和流动性，但 FX
是全球市场，并非所有市场同时关闭。因此不能把"本地假期"直接等同于"外汇市场关闭"。

应研究市场活动由正常到下降、低活动、恢复再回到正常的过程，并按货币对和时段分别验证。

### 5.3 候选 Regime 状态

讨论提出以下状态名称：

-   `TRADE_ALLOWED`
-   `REASSESSMENT`
-   `ENTRY_PAUSED`
-   `RECOVERY_CONFIRMATION`
-   `UNKNOWN_PATTERN` → `NO TRADE`

Regime Controller 综合 Daily Anchor、Rolling MC、Fib、Kalman、Calendar
Context、Observed Context 和数据质量，决定当前是否允许新 Entry。

应设计确认条件和
hysteresis（滞回），避免状态在边界附近频繁切换。过期、异常或相互冲突的数据应使新
Entry 暂停，而不是静默地继续使用旧结果。

以上是候选状态与职责，具体转移条件、阈值和优先级尚未最终确定。

## 6. 交易生命周期研究：最近 30 天

本系列讨论提出一个独立研究任务：提取最近 30 天 OANDA
交易，分析开仓到平仓的完整价格路径。

### 6.1 研究问题

-   某些时段开仓后，是否更容易先触及 SL？
-   即使最终价格朝原交易方向运行，是否经常在到达目标前先触及 SL？
-   TP 后的下一笔交易是否更容易
    SL？若是，是否与趋势耗尽、过度延伸、regime 变化或其他因素相关？
-   Bot 在维护/重启后，已有仓位是否会抑制新 Entry 的评估或提交？
-   不同货币对、方向、星期、交易时段和市场环境下，交易生命周期是否存在可重复差异？

### 6.2 不能只统计最终盈亏

每笔交易应尽量关联 Broker
的真实交易记录、退出交易事务和可执行报价价格路径。

候选字段：

-   Trade ID、Instrument、Direction；
-   Entry time / Entry price；
-   Exit time / Exit price；
-   SL / TP；
-   Realized P/L；
-   Closing transaction / Exit reason；
-   Entry spread；
-   Holding duration；
-   MAE（最大不利变动）；
-   MFE（最大有利变动）；
-   达到 MAE / MFE 的时间；
-   到 SL / TP 的时间；
-   平仓后预定义观察窗口内的价格变化；
-   Pair、weekday、session；
-   对应市场 Context / Regime（若当时有可靠记录）。

"方向后来正确"必须用事先定义的平仓后观察窗口和价格标准来表达，不能用事后任意挑选的时间段定义。

### 6.3 价格侧与数据要求

-   现有 `data/fetch_oanda.py` 主要获取 Mid OHLC。
-   对 SL/TP 触及顺序的研究，Mid 数据可能不足；需要考虑 Bid/Ask
    可执行价格侧及当时 spread。
-   BUY/SELL 的止损触发应按相应可执行报价侧验证，不能仅凭 Mid candle
    宣称 SL 已被触及。
-   30 天 M1 数据量约为每个连续交易品种 43,200
    根分钟线，需处理周末、缺口、未完成 candle 和分页。
-   所有内部时间统一使用 UTC；分析交易时段时再转换到明确的 IANA
    时区，并考虑 DST。
-   Session 定义必须写清楚；可使用主要时段分类并额外标记
    overlap，避免含糊的多重归类。

### 6.4 统计方法

至少分别报告：

-   SL rate；
-   TP rate；
-   Loss rate；
-   Expectancy；
-   样本数和时间范围；
-   按时段、货币对、方向等分组的结果；
-   估计不确定性，避免小样本下过度下结论。

核心比较之一：

``` text
P(SL first | Session)
```

不能只比较每个时段亏损笔数，因为各时段交易机会数量可能不同。盈利交易也必须纳入分析，否则无法判断某个时段是否同时拥有更多机会和更多风险。

### 6.5 当前代码检查结论

在当前 `forex_oanda_v7` checkout 中，用户确认：

-   `data/fetch_oanda.py` 是行情 candle 获取逻辑；
-   `execution/oanda_conn.py` 主要处理当前 open trade / position；
-   `check_order_details.py` 检查当前持仓和 SL/TP 细节；
-   repo-wide grep 未发现
    `ClosedTrades`、`AccountTransactions`、`TransactionIDRange`
    等历史平仓/事务查询实现。

因此，**不再在当前项目中继续寻找历史交易提取程序**。用户表示明天会找到并提供之前那段历史数据程序。届时应先检查并复用它，而不是重复造轮子。

## 7. 跨项目模块化复用：新增的明确要求

用户明确提出：

> 以后做子项目一定要模块化。供各个项目复用！！！

这是一项后续开发的硬性设计要求。

含义：

1.  新子项目不能只写成某个主项目中的一次性脚本。
2.  将可复用能力设计成边界清楚的独立模块/包。
3.  数据获取、数据标准化、交易生命周期分析、市场状态估计、MC/Fib
    计算、报告输出等职责应合理分离。
4.  模块之间通过明确的数据契约和接口交互，避免依赖某个项目的内部目录结构、全局变量或隐式配置。
5.  OANDA
    连接器/数据源适配器与通用分析逻辑分开；通用分析核心不应被某个券商
    API 锁定。
6.  配置、时区、数据质量、日志、错误处理和版本信息应显式化。
7.  模块应有独立测试和可重复运行的 Demo/示例。
8.  被多个项目复用的模块应有明确版本和兼容性约定。

具体采用 monorepo、独立 Python
package、共享库还是其他目录组织方式，尚未决定。明天的开发计划应选择最简单、可维护、不过度工程化的方案。

## 10. 明日工作顺序

### Step 1 --- 找回历史交易提取程序

用户明天提供之前找到的程序。先审查其：

-   数据来源与 API；
-   时间范围和时区；
-   是否包含已平仓交易；
-   是否能关联真实 SL/TP closing transaction；
-   是否包含完整交易 ID 和价格字段；
-   是否能安全地只读连接 Practice；
-   是否存在 Live 访问或下单副作用。

不要先写新的交易历史提取脚本。

### Step 2 --- 其他 LLM 简单讨论（最多三轮）

目标不是让多个模型重新设计一个庞大系统，而是检查关键遗漏和方案可执行性。

建议限制：

-   最多三轮交流；
-   所有模型使用同一份本总结作为输入；
-   只讨论关键架构、模块复用、数据契约、最小 Demo 路径和主要风险；
-   要求指出证据、假设和未知项；
-   不接受无边界扩展或重复提出已明确的原则；
-   第三轮结束后停止讨论，进入决策。

### Step 3 --- 形成最简且最终的开发计划

计划应包含：

1.  最小模块边界与复用方式；
2.  明确的输入/输出契约；
3.  先做什么、暂不做什么；
4.  每个阶段的可运行交付物；
5.  自动化测试和数据质量检查；
6.  Practice Demo 验证方法；
7.  日志、回放和审计要求；
8.  验收标准和停止条件；
9.  风险与回滚方案。

最终计划应足够简单，可以直接交给 TRAE 或其他编码 Agent
执行，不再陷入长时间的规格反复。

## 11. 当前阶段的结论

1.  目标是建立持续、自适应、统计驱动的市场观察与 Entry
    许可系统，而不是增加一个孤立指标。
2.  Daily Anchor 与 Rolling MC/Fib 应分开维护，不能混用坐标或覆盖基准。
3.  Kalman 用于状态估计和不确定性表达，不单独产生交易信号。
4.  Calendar Context 与 Observed Context 分离；节假日不等于自动停交易。
5.  Regime Controller 负责综合信息并管理 Entry 许可；未知模式采取 No
    Trade。
6.  第一轮只在 OANDA Practice Demo 控制新 Entry，不改变已有持仓管理。
7.  交易历史研究必须分析完整价格路径、Bid/Ask、MAE/MFE 和 SL/TP
    触及顺序，而不只是最终盈亏。
8.  当前项目没有找到历史交易提取实现；等待用户明天提供旧程序。
9.  **以后所有子项目必须模块化，并优先设计成可供多个项目复用的能力。**
10. 明天最多三轮 LLM 简单讨论，然后形成最简、最终、可执行的开发计划。

**本文件是讨论总结，不是最终技术规格，也不授权直接修改现有交易策略或连接
Live 账户。**
